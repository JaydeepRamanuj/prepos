## Question
"Tell me about a time you had to pick up a new technology, framework or codebase quickly. How did you approach it?"

## Interview Answer
When I joined [company], the project used [technology, e.g. "the Next.js App Router with Server Components"], which I had only [taught at a basic level / used in tutorials], and I was expected to ship [a feature] within [two weeks]. I set myself a plan. First, I read the official docs for the core concepts, [e.g. "server vs client components, data fetching and caching"], instead of random tutorials. Then I built a tiny throwaway app that used exactly those features. Then I read how our codebase did the same things. I used an AI coding agent as a tutor, not a crutch: I'd ask it to explain a pattern in our code, then check that against the docs, and I wrote the first version of the feature myself so I'd really understand it. I kept a short notes file of gotchas, [e.g. "where 'use client' boundaries go"]. I shipped the feature [on time / in N days], and my notes became part of the onboarding doc for the next joiner.

## Explanation
### What the interviewer is really assessing
- **Learning method.** Do you have a repeatable way to learn, or do you just Google until it works?
- **Speed with depth.** Did you get productive fast *and* understand what you built?
- **AI judgement.** For a candidate who uses agents daily, they want to see you learning *with* the tool, not outsourcing understanding to it.

### STAR template
- **Situation** — The tech, your starting level, the pressure: [tech], [prior exposure], [deadline / why it mattered].
- **Task** — What you had to deliver: [feature / fix / migration].
- **Action** — Your learning loop: [official docs for core concepts] → [tiny prototype] → [read existing code] → [build the real thing] → [notes / ask a teammate]. Mention how you used AI and how you verified it.
- **Result** — Delivered [what, when], plus a reusable artefact: [docs, template, talk].

### Story ideas from your background
- Learning the App Router, TanStack Query, Tailwind v4 or TypeScript on the job.
- Trainer years: learning a topic well enough to *teach* it within a week. Teaching is the hardest test of understanding.
- Side projects: picking up Postgres, Redis or Firebase for a full-stack app.
- Learning an unfamiliar legacy codebase fast enough to fix a production bug.

### Variants of the question
- "How do you keep up with frontend changes?"
- "How do you approach an unfamiliar codebase?"
- "Tell me about something you learned recently."

## Follow-ups
- **How do you know when you've learned enough to start?** — When you can build a small working example and explain the core concepts without notes; the rest you learn while building.
- **How do you stop AI from teaching you something wrong?** — Cross-check against official docs, run the code, and be able to explain every line before shipping it.
- **What are you learning right now?** — Have a current, honest answer (e.g. backend topics from your side project).

## Common Mistakes
- "I watched a YouTube course" as the whole method.
- No result. Learning is only interesting if it led to delivery.
- Implying the AI did the work and you supervised. Show your own understanding.

## Tips
- Name the loop: **docs → prototype → real code → teach it back**. The "teach it back" step is your trainer edge.
- Mention a specific gotcha you hit. It proves the story is real.
