## Question
A teammate opens a 900-line PR that was mostly generated by an AI agent. It compiles, tests pass and the demo works. How do you review it, and what extra risks do you look for?

## Interview Answer
I review AI-generated code with the assumption that it is plausible-looking but not necessarily correct, so I shift effort from "is this readable?" to "is this right, necessary and safe?". First I check the PR itself: is it a sensible size, does the description explain intent, and did the author actually understand and test it? Large generated diffs should be split. Then I verify the behaviour rather than trusting the green checks: read the tests critically (do they assert real behaviour or just mirror the implementation, were assertions weakened or mocks overused?), run it, and probe edge cases. I look for typical AI failure modes: hallucinated or deprecated APIs and wrong library versions, silent error swallowing, over-engineering and duplicated helpers instead of reusing existing code, inconsistent conventions, unnecessary dependencies, security gaps (missing authorisation, unvalidated input, secrets, injection), performance traps like N+1 queries or effects that refetch, and unrelated changes. The author stays accountable: "the AI wrote it" isn't an explanation. I give feedback that improves the system too, by converting repeated problems into lint rules or instructions.

## Explanation
### Review order
1. **Intent and scope**: read the description and ticket. Does the diff do only what was asked? Flag drive-by refactors, reformatting, deleted code or tests, new dependencies.
2. **Architecture fit**: does it follow existing patterns (data fetching, error handling, folder structure) or invent a parallel approach? AI often adds new helpers because it didn't find the existing one.
3. **Tests**: new behaviour covered? Do they fail without the change? Any `skip`, loosened assertion, snapshot churn, or mocking of the unit under test?
4. **Correctness**: trace the main path and error paths; check boundary conditions, async races, null handling, timezones and units.
5. **Security and data**: authorisation on every server entry point, validation of inputs, no secrets, safe rendering, no sensitive data logged.
6. **Performance and cost**: queries in loops, missing indexes, unbounded lists, effect dependencies, bundle size.
7. **Maintainability**: naming, dead code, comments that restate code, excessive abstraction.
8. **Run it**: check out the branch, execute the flow, try bad input.

### Common AI-code smells

| Smell | What to look for |
|---|---|
| Hallucinated API | method or option that doesn't exist or belongs to another version (check docs/types) |
| Outdated pattern | old React/Next.js APIs, deprecated config, wrong import paths |
| Swallowed errors | `catch {}` or `catch (e) { console.log(e) }` with success returned |
| Overbroad types | `any`, `as` casts, `// @ts-ignore` to silence the compiler |
| Duplication | new util that already exists elsewhere |
| Plausible but wrong logic | off-by-one, wrong operator, inverted condition that tests don't cover |
| Test theatre | tests that assert the mock was called, not the outcome |
| Scope creep | unrelated files touched, formatting churn |
| Insecure defaults | missing auth check, permissive CORS, string-built SQL |
| Comment noise | comments narrating obvious code, stale TODOs |

### Making review tractable
- Ask for **small PRs** and stacked changes; a 900-line generated diff is unreviewable as one unit.
- Let tools do the mechanical part: types, lint, tests, security scanners, and AI-assisted review as a first pass. Humans then focus on design and risk.
- Ask the author questions to confirm understanding ("why this approach over the existing `useOrders` hook?"). If they cannot explain it, it is not ready.
- Require evidence: screenshots, test output, or a short note on how it was verified.
- Review the **prompt and plan** if the author shares them; they reveal assumptions.

### Feedback that scales
When the same issue appears more than once, don't just comment: add a lint rule, a test helper, or a line in `AGENTS.md` (see the "fix the system" question). Treat AI review bots as helpers whose findings still need verification, since they produce false positives and miss real bugs.

### Accountability and culture
The author owns the change regardless of who or what typed it. Teams should agree that submitting code you haven't read and understood isn't acceptable, and that reviewers may ask to split or redo oversized generated PRs.

## Follow-ups
- **Should AI review replace human review?** — It is a useful first pass for mechanical and common issues, but humans still own judgement about intent, design and risk.
- **How do you review a test written by the same agent that wrote the code?** — Check that it fails against the old behaviour and asserts outcomes, and prefer tests derived from the requirement.

## Common Mistakes
- Approving because CI is green.
- Reviewing style while missing a missing auth check.
- Accepting oversized diffs.

## Tips
- Say "verify, don't skim: intent, tests, security, then style".
